## Achados

Cada achado carrega a fonte (arquivo, commit, ou saída de comando) e uma disposição.

### Visão agregada — arquivo "deus" no sidecar

- **Achado:** `apps/desktop/sidecar/src/index.ts` tem 1.269 linhas e 31 rotas HTTP inline (`grep -c 'req.method ==='`), concentrando roteamento, validação de entrada e lógica de negócio de todos os domínios (operadores, sessão, cardápio, mesas, comandas, itens, pagamentos, caixa, pareamento, sync). É 68% de todo o código-fonte do sidecar (1.269 de 1.855 linhas) — nenhum outro arquivo do pacote passa de 191 linhas (`cloud-sync-client.ts`); a maioria fica entre 17 e 81 linhas.
- **Fonte:** `wc -l apps/desktop/sidecar/src/*.ts` (medido nesta sessão); crescimento confirmado pelo `git_evidence.py` — 14 commits distintos tocaram o arquivo, +1.387/-118 linhas ao longo do épico, mais que qualquer outro arquivo de código do projeto.
- **Disposição:** *deferir*. Funciona corretamente (49 testes indiretos via `sync-engine` + smoke tests + `concurrency-scenario.mjs` validam o comportamento), mas o tamanho já dificulta navegação e vai piorar a cada novo endpoint. Candidato natural a quebrar por domínio (`routes/orders.ts`, `routes/catalog.ts`, `routes/pairing.ts`, etc.) — nenhuma urgência, mas vale abrir como item de ação antes do próximo épico que for mexer pesado no sidecar.
- **Lição de processo:** nenhum limite de tamanho de arquivo foi estabelecido no `CLAUDE.md`/convenções do projeto. Não é um gate ausente crítico (o projeto é solo, sem revisão de PR de terceiros), mas registrar aqui evita que o próximo ciclo repita o padrão sem perceber.

### Visão agregada — renomeações registradas como reescrita completa

- **Achado:** pelo menos 5 arquivos mostram o padrão exato `+N linhas / -N linhas` idêntico no `git_evidence.py` (`apps/desktop/src/App.css`→`app.css`: +173/-173; `packages/sync-engine/test/outros-eventos.test.ts`→`other-events.test.ts`: +161/-161; `packages/shared-types/src/eventos.ts`→`events.ts`: +143/-143; `arch-4.2-conflito-de-mesa.test.ts`→`arch-4.2-table-conflict.test.ts`: +107/-107 no pacote atual e +108/-108 no espelho do spike) — a assinatura de uma renomeação de arquivo feita como delete+recria em vez de `git mv`, que o git não detectou como rename.
- **Fonte:** `git_evidence.py --range 4b825dc6..fa02228`, campo `files`, comparando `added`/`deleted` por caminho.
- **Disposição:** *aceitar como está*. É o resultado esperado da migração de nomenclatura pra inglês (decisão retroativa do usuário registrada em `feedback_english_naming.md`), já commitada há muito tempo — reescrever o histórico do git não vale o custo. Não afeta o comportamento do sistema, só infla o histórico de blame desses arquivos específicos.
- **Lição de processo:** numa próxima renomeação em massa, usar `git mv <old> <new>` (ou `git add` do novo + `git rm` do antigo na mesma operação, que o git ainda consegue detectar como rename por similaridade de conteúdo) preserva a atribuição por linha no `git blame`/`git log --follow`.

### Visão agregada — reconciliação spec-vs-implementado

- **Achado:** `docs/architecture.md` §6 descreve os limites de plano como guardados "em uma tabela `planos`/`assinaturas`". O M10 implementou isso como colunas (`max_concurrent_orders`, `max_terminals`) direto na tabela `establishments` — uma divergência deliberada, já documentada explicitamente na nota de fechamento do M10 ("Decisão deliberada: em vez de uma tabela `plans` separada...").
- **Fonte:** `docs/architecture.md` §6 vs. `apps/backend/src/schema.sql` (tabela `establishments`) vs. nota de fechamento do M10 em `docs/implementation-plan.md`.
- **Disposição:** *aceitar como está* — a divergência já foi julgada e registrada no momento em que aconteceu, com justificativa (sem tiers nomeados/cobrança no MVP, tabela separada seria estrutura sem consumidor). Não é uma reconciliação pendente, é uma decisão já tomada; registro aqui só confirma que o rastro de decisão está intacto.

### Padrão entre milestones — onde os bugs reais se concentraram

- **Achado:** contando os achados reais descritos nas notas de fechamento do `implementation-plan.md` por milestone: M0 (1 — bug de `execFileSync`/`.cmd` só em Windows real), M3 (2), M5 (2), M6 (1 + 1 auto-infligido em teste), M7 (1), M9 (2), M10 (2), **M12 (6)** — contra **zero** bugs registrados em M1, M2, M4 (só o incidente de processo, não um bug de código), M8 e M11. Os milestones com zero bugs são os que **estenderam um padrão já validado** dentro da mesma topologia de implantação (mais um endpoint CRUD, mais uma tela). Os milestones com mais bugs são os que **mudaram a topologia de implantação** e a testaram pela primeira vez: M9 (sync entre terminais pela primeira vez), M12 (rede entre duas MÁQUINAS físicas reais e empacotamento Windows real pela primeira vez desde o Spike 1).
- **Fonte:** notas de fechamento de cada milestone em `docs/implementation-plan.md` (M0 linha ~24, M9 "Achado durante o teste do M9", M10 "Dois achados durante o teste", M12 "seis achados reais").
- **Disposição:** *lição de processo*, não uma correção de código. O M12 encontrou que o bind em loopback-only do sidecar quebrava o sync LAN entre máquinas físicas desde o M9 — isso ficou **latente por 3 milestones** (M9, M10, M11) porque todo teste de multi-terminal usou processos na mesma máquina em portas diferentes, nunca duas máquinas de verdade. De forma similar, o CI de Windows não rodou nem uma vez entre o Spike 1 (M0) e o M12 — quatro achados de empacotamento (versão de TypeScript conflitante, script de build sensível a plataforma, install redundante de workspace, falta de build dos pacotes locais) ficaram latentes por 11 milestones inteiros.
- **Ação recomendada:** quando um épico futuro introduzir uma topologia de implantação nova (nova forma de o software rodar/se comunicar — outro processo, outra rede, outro SO), validar essa topologia **no próprio milestone que a introduz**, não só na revisão de hardening no final. Um teste de "duas máquinas físicas reais" ou "CI nativo na plataforma alvo" custa pouco a mais feito cedo e exponencialmente mais caro descoberto tarde (7 iterações de CI só pra destravar o Windows no M12).

### Verificação de comportamento

- **CI real do Windows:** [run 35664866037](https://github.com/jrsousa95/passa-a-regua/actions/runs/35664866037) — sucesso completo (build do binário SEA nativo, smoke test de negócio completo, instalador `.msi`/`.exe` gerado), ~12 minutos, confirmado via `gh run view`.
- **Cenário de concorrência real (`npm run test:concurrency`):** executado múltiplas vezes nesta sessão contra dois sidecars reais pareados por LAN — os três cenários (conflito de mesa simultâneo, item concorrente, resiliência à queda do host) passaram de forma consistente e repetível.
- **Suíte de testes unitários:** 49 testes (8 em `shared-types`, 41 em `sync-engine`) passando, confirmado nesta sessão via `npm test -- --run` em ambos os pacotes.
- **Typecheck:** `backend`, `sidecar` e `desktop` (frontend) typecheckando limpo, confirmado nesta sessão.
- **Sessão real do usuário:** durante toda a sessão de implementação (M9-M12), o processo `tauri dev` real do usuário na porta 4550 nunca foi tocado por nenhum teste — só instâncias isoladas em portas alternativas foram usadas para validar mudanças no sidecar. Efeito colateral encontrado e corrigido no meio do caminho: o processo real do usuário ficou "congelado" numa versão pré-M5 por várias sessões (nunca reiniciado), e um processo órfão bloqueou silenciosamente um restart — ambos diagnosticados e corrigidos ao vivo (ver `feedback_sidecar_restart_needed.md` na memória do projeto).
