# Adversarial review — architecture.md §3.4/§3.5/§4.4, §5 (9.8/9.9), §11

Reviewer lens: attack the spine. Assume two developers (or two AI agents) each build a piece of Épico 9 independently, obeying only what is literally written. Where do they diverge or produce a wrong number? Read-only — no fixes applied, findings only.

Grounding evidence used beyond the doc itself:
- `packages/sync-engine/src/reconciliation.ts` — the `order_closed` handler and the `tableToCanonicalOrder` cleanup bug history (§4.2's real precedent).
- `packages/shared-types/src/events.ts`, `common.ts` — event envelope, `baseEventSchema`.
- `packages/sync-engine/src/reporting.ts` — `computeCashRegisterSummary`, `localDateKey`.
- `apps/desktop/sidecar/src/terminal-identity.ts` — how `terminal_id` is actually created and persisted.
- `apps/backend/src/index.ts` — `/register`, `/terminals`, terminal pairing/plan-limit logic.

## Verdict

**Not safe to hand to two independent implementers as-is.** §4.4's "sessão de caixa não é um caso de conflito estilo §4.2" is the weakest claim in the new material: it's asserted by fiat about *physical* reality (one drawer, one terminal) with zero mechanism enforcing that the assumption holds, on a system whose entire reason for existing is that terminals *can't* coordinate reliably. The §3.4 `[ASSUMPTION]` is correctly flagged as unconfirmed, but even if confirmed, the mechanism proposed to implement it (wall-clock window correlation, frozen into an immutable event) has no correction path and quietly contradicts the doc's own §3.1 rule that wall-clock timestamps are never used for correctness-critical decisions. §3.5's range function has at least three unstated behaviors that two reasonable implementers would fill in differently. None of these are addressed by adding tests later — they're gaps in the decision itself.

---

## Finding 1 — `terminal_id` is not a stable proxy for "one physical drawer," and §4.4 needs it to be

`apps/desktop/sidecar/src/terminal-identity.ts` shows `terminal_id` is a random UUID generated on first boot and persisted in a plain file (`terminal-id`) in the local data dir — **not** derived from hardware, not issued by the backend at pairing (pairing/credential issuance is a separate, later concern per its own comment). Consequences §4.4 doesn't address:

- **Terminal replacement mid-shift.** The caixa PC crashes/disk fails with a `cash_session` open. Staff can't wait — they open the app on a spare tablet to keep taking cash. The spare tablet has no `terminal-id` file, so it mints a *new* `terminal_id`, and the "one open session per terminal" route check trivially passes (it has no local open session). Now two `cash_session` aggregates are open concurrently for what is operationally the *same drawer*. This is structurally identical to the §4.2 bug class (two terminals independently satisfying a *local* invariant that was actually supposed to be *global*) — the exact bug this project has already shipped and had to fix once for tables. §4.4 dismisses this by asserting the drawer "não é compartilhada com outro terminal," but nothing in the system enforces or even represents that mapping; it's a human convention, not an invariant.
- **No merge/resolution rule exists for this case**, unlike `order_opened`. `reconciliation.ts` has `tableToCanonicalOrder` + `mergedInto` + `mergeWarnings` specifically to resolve two `order_opened` for the same table deterministically and *visibly*. §3.4's `cashSessions: Map<string, CashSessionState>` has no equivalent — if two `cash_session_opened` events for the same `terminal_id` (or, worse, for what a human considers "the same drawer" across two `terminal_id`s) end up in a merged log, both simply exist as separate open entries forever. Two implementers would each invent their own tie-break (first by HLC wins? most recent wins? surface both as an error?) and neither would be contradicting anything written.
- **Reinstall loses the mapping entirely**, not just changes it: since `terminal_id` lives in one file with no backup, a full reinstall/disk-loss doesn't just get a new id — it also loses the entire local `events` table, so recovery of "what was open" depends entirely on whether that terminal had already synced. If it hadn't, the open session (and any withdrawals recorded on it) simply vanishes from that terminal's perspective while still existing, unresolved, wherever it last synced to.

**What's missing from the doc:** an explicit statement of what "one open session" is actually scoped to in the real world — per `terminal_id` (as written) or per *establishment* (the far more common real POS assumption: one cash drawer per bar, regardless of how many terminals exist) — and, if per-`terminal_id`, a defined resolution rule for the case where two open sessions for the intended-to-be-same drawer sync into one log. Right now this is a business decision (drawer-to-terminal cardinality) smuggled in as an architecture footnote, not confirmed with the owner the way §11 already flags the §3.4 assumption for confirmation.

## Finding 2 — `expectedAmountCents` window correlation both violates the doc's own §3.1 rule and has no correction path

§3.4's `[ASSUMPTION]` computes `expectedAmountCents` from cash payments of orders `closing.closedAt` inside `[openedAt, closedAt]`, and — critically — this number gets **written once into the immutable `cash_session_closed` event payload** at close time (per the event table in §3.4: `expectedAmountCents` is a payload field, not a query-time value). Concrete failure cases:

1. **Late-arriving sync, frozen forever.** Waiter tablet (offline all day) closes a cash order at 14:00, inside the caixa session's window, but doesn't sync to the caixa terminal until 18:00 — *after* the caixa already closed the session at 15:00 and wrote `expectedAmountCents` using only what it had seen by then. Because events are append-only and there's no `cash_session_closed`-correction event defined (unlike items, which have `item_canceled`/`item_note_updated` for exactly this kind of "the original write needs adjusting" case), the recorded `differenceCents` is permanently wrong with **no defined way to fix it** — not even a manual audit adjustment event exists in the new event set.
2. **Violates §3.1's own foundational rule.** §3.1 is explicit: `created_at` ("timestamp de parede... nunca usado para ordenação de conflito") must never drive correctness decisions — only HLC can, because wall clocks across terminals aren't trustworthy. `ClosingState.closedAt` in `reconciliation.ts` even carries a comment reiterating this ("nunca pra ordenação/conflito, isso é papel do hlc"). §3.4's `[openedAt, closedAt]` window is built from exactly those wall-clock fields, now used to decide **which orders' money counts toward a monetary reconciliation** — the single most correctness-sensitive computation in the whole feature. A terminal with a fast clock closing an order at what it thinks is 15:01 (one minute after the caixa's `closedAt`) silently drops that cash from the session's expected total; a terminal with a slow clock could pull in an order that, causally, happened after the session closed. This is a real internal contradiction, not just a risk — the doc should either justify the exception explicitly or fix the mechanism.
3. **No terminal filter on the candidate orders at all.** As literally written, the correlation is "orders closed in cash with `closing.closedAt` in the window" — full stop. It does not say "closed *by the session's own terminal*" or filter by the order's `terminal_id`. Combined with Finding 1 (nothing prevents two sessions being open concurrently, whether on the same intended drawer or two genuinely different ones), an order closed by a third terminal (a waiter tablet) during an overlap window gets counted into **every** open session whose window contains it — double-counted across two caixa sessions' `expectedAmountCents`, not just wrong in one of them. Two implementers reading the assumption literally would both write this same double-counting query, because nothing in the text tells them to filter by terminal.

**What's missing:** (a) explicit terminal-scoping of the candidate-order query (not just "assume only one terminal receives cash," which is a human-behavior assumption, but an actual filter in the query as defense-in-depth); (b) a decision on what happens when a cash order syncs in *after* the session that should have counted it has already closed — silently wrong forever, a warning UI element (mirroring `mergeWarnings`), or a blocking rule that a session can't close while there are known-unsynced-elsewhere risks; (c) reconciling the window-based approach with §3.1's no-wall-clock-for-correctness rule, or an explicit, argued exception.

## Finding 3 — offline-first multi-terminal sync can still produce the exact §4.2 conflict shape for cash sessions

This is really Finding 1 viewed from the sync angle, called out separately because §4.4 explicitly tries to preempt it and the preemption doesn't hold up. §4.4's argument is: a table is a *shared* resource (hence real conflicts, hence HLC-merge), a cash drawer is *not* shared between terminals (hence no conflict class exists). But "shared or not" isn't a property of the software — it's a property of how the humans use it, and this project's whole premise (§1) is that terminals operate independently offline and only find out about each other's actions on sync. Two terminals, unable to see each other, each locally satisfying "no open session on me" is *precisely* the mechanism that produced the §4.2 bug for tables — the doc even names the mechanism correctly in §4.2's write-up and then declines to apply the same scrutiny to §4.4. The doc should either (a) demonstrate the drawer really is architecturally exclusive to a `terminal_id` for the life of the establishment (it currently isn't — see Finding 1's reinstall case), or (b) adopt a resolution rule symmetrical to §4.2 (deterministic HLC-based canonical session + non-blocking merge warning) instead of asserting the conflict can't happen.

## Finding 4 — `computeCashRegisterSummaryForRange` has at least three unstated behaviors

`reporting.ts`'s existing `computeCashRegisterSummary` filters with exact string equality (`localDateKey(...) === dateKey`) and separately returns `pendingOrders` as *all* currently-open orders, unscoped to the date at all. §3.5 says the range function should share an "internal helper" for the aggregation math but doesn't pin down:

1. **Inclusive/exclusive bounds.** Nothing says whether `toDateKey` is inclusive. `YYYY-MM-DD` string keys compare lexically fine either way, but one implementer doing `from <= key <= to` and another doing `from <= key < to` will silently disagree on the last day of every range — and there's no test yet to catch it since the function doesn't exist.
2. **`pendingOrders` semantics under a range.** In the single-day function, `pendingOrders` is *not* filtered by date — it's just "everything still open," included in a daily summary as a courtesy. Under a range, does that stay "all open orders regardless of range" (as the existing code implies) or does a reasonable implementer scope it to orders opened within the range? The doc doesn't say, and the field's existing behavior for a single day doesn't obviously generalize.
3. **Interaction with the per-operator report (9.6).** §3.4 adds `closing.operatorId` specifically to support 9.6, but §3.5's function signature is `(orders, fromDateKey, toDateKey)` — no operator parameter. That implies the caller pre-filters `orders` by `o.closing?.operatorId` before calling the summary function. But `pendingOrders` are, by definition, not closed and have no `closing.operatorId` — pre-filtering the input array by operator would make `pendingOrders` always empty for a per-operator report (arguably correct) while an implementer who instead adds an `operatorId` parameter *inside* the shared helper would get different, inconsistent filtering semantics for the two report types. Nothing pins down which shape 9.6 actually takes.
4. **Timezone/day-boundary drift between sidecar and backend gets worse at range scale.** `localDateKey`'s own comment already accepts "sidecar: fuso da máquina do usuário; backend: fuso do servidor — ok pro MVP" as a known quirk for the single-day case. For a *range* report — and especially for 9.8's consolidated multi-terminal report, which explicitly reuses the backend endpoint — an order closed near midnight can land in a different calendar day (and therefore inside vs. outside the requested range) depending on whether the sidecar's local timezone or the backend server's timezone computed the key. This was a tolerable rounding error for one day; it becomes a visible reconciliation mismatch when a bar owner compares "my terminal's period report" against "the consolidated cloud report" and the totals don't match at the edges.

**What's missing:** pin down inclusive/exclusive range bounds, `pendingOrders` scope under a range, and whether per-operator filtering happens outside or inside the shared helper — plus an explicit note (even if deferred) that day-boundary computation differs between sidecar and backend and range reports will surface it more than the existing daily report does.

## Finding 5 — §5's "no new architecture decision" for 9.8 assumes the backend already materializes cash-session state, which it doesn't yet

§5 states 9.8 (multi-terminal consolidated report) "reaproveita o endpoint `GET /reports/cash-register`... existente desde o M11 sem UI associada." That endpoint was built (M11) before `cash_session`/withdrawals/deposits existed, and calls `computeCashRegisterSummary` over `orders` only — there is no mention anywhere in §3.4 of the backend's Postgres projection replaying the four new `cash_session_*` events. If 9.8 is meant to show session-level facts (open/close times, `differenceCents`, sangria/suprimento) consolidated across terminals — which is the whole point of a "cash session" report, not just an order-sales report — the backend needs a Postgres-side `CashSessionState` projection that doesn't exist yet and isn't scoped anywhere. If 9.8 is *only* meant to reuse the existing order-based summary (no session-level fields at all), that's a much smaller story than "cash register report" implies and should be stated as a scope limitation, not left implicit. Either reading is defensible from the text, which is exactly the problem: two implementers would build 9.8 to different feature scopes.

## Minor/secondary note — plan-limit interaction with terminal replacement

Not a §3.4/4.4 issue directly, but relevant to Finding 1: `apps/backend/src/index.ts`'s `/terminals` endpoint counts registered terminals against `plan.maxTerminals` and has no deregistration path visible in the reviewed code. A terminal replaced after data loss (Finding 1) doesn't just orphan a cash session locally — it also permanently consumes a paid-plan terminal slot unless something elsewhere deregisters the old id. Worth a one-line flag if not already covered elsewhere in the plan-limits section (§6).

## Recommended tightening (for whoever turns this into confirmed ADs before 9.1-9.9 are broken into tasks)

1. State explicitly whether "one open cash session" is scoped per-`terminal_id` or per-establishment, and if per-`terminal_id`, add a deterministic resolution rule (mirroring §4.2: canonical-by-HLC + non-blocking merge warning) for the case where two turn out to be open concurrently for what was meant to be one drawer.
2. Either drop the wall-clock window correlation in favor of an explicit order→session link (a small additive field, same append-only spirit as the `ClosingState.operatorId` retrofit already proposed), or keep the window but (a) filter candidate orders by `terminal_id` explicitly, and (b) define what happens when a relevant order syncs in after the session already closed.
3. Pin down `computeCashRegisterSummaryForRange`'s inclusive/exclusive bounds and `pendingOrders` scope before it's implemented, and decide whether per-operator filtering (9.6) happens outside or inside the shared helper.
4. State explicitly whether 9.8 requires a new backend Postgres projection for `cash_session_*` events, or is scoped to order-sales-only data reusing the M11 endpoint as-is.
